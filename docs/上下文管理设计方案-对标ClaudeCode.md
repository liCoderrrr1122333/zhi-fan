# 上下文运行设计

Claude Code 式循环给我的启发是：上下文不是一个越塞越满的袋子，而是模型在当前这一步能看到的工作状态。状态里既有规则和历史，也有工具刚返回的结果。结果可能成功、为空，也可能是错误。

## 当前怎样组织上下文

每次咨询都会重新拼接基础运行规则、人工维护的业务规则和策略总纲。会话历史保存用户消息与最终回复。本轮工具调用和返回结果只留在本轮循环及运行轨迹中。策略样本按当前问题做语义召回，不把整库倒进提示词。

这样做有两个好处：重要规则每轮都在；样本增加时，单轮携带的样本数量仍然可控。代价是跨轮工具细节不会自动成为长期记忆，需要通过工单或人工确认的纠偏来沉淀。

## 曾经踩过的坑

早期把全部样本塞进提示词，样本少时看起来很省事。样本多了，相关的几条反而被噪声淹没；相似但有差异的样本会互相拉扯；长度、延迟和费用一起增加。后来改为服务时只召回最相关的几条，全量样本只用于归纳总纲。

另一个坑是把“硬规则”和“经验样本”混在一起。新样本会变，业务红线不能跟着摇摆。因此人工维护的规则始终高于总纲和具体样本。

## 长会话下一步怎么做

当前还没有自动压缩长会话。下一步计划验证三件事：

1. 把已确认的用户事实、已完成动作和待解决问题压成结构化状态。
2. 区分本轮工作状态、可检索策略和长期业务规则的生命周期。
3. 为摘要保留来源，出现偏差时能追溯到原始消息。

压缩不能只看少用了多少令牌。摘要如果丢掉一个关键事实，会直接影响下一轮决策，因此需要用评测集验证。

## 与循环的对应关系

| 阶段 | 当前实现 |
| --- | --- |
| 观察 | 读取规则、历史、相关策略和工具结果 |
| 执行 | 模型选择工具，系统执行 |
| 校验 | 结果、空结果或错误进入下一轮上下文 |
| 纠偏 | 人工意见触发重答，确认后才写入策略库 |

目前的“反思”仍是人机协同过程，不是无人审批地改写系统规则。
