# 知返后续路线图

> 这份路线图解决一个核心问题：知返如何从“能运行的智能体演示项目”，逐步变成“能证明自己在变好的智能体系统”。

## 一、接下来只围绕一条主线

知返暂时不追求功能越来越多，而是验证这条闭环是否成立：

```text
提出问题
  ↓
智能体观察上下文并调用工具
  ↓
得到回复和运行轨迹
  ↓
发现错误或不稳定行为
  ↓
人工纠偏并确认
  ↓
策略进入记忆
  ↓
自动评测新旧版本
  ↓
证明下一次确实变好
```

真正值得写进项目和简历的成果，不是“增加了几个按钮”，而是能够回答：

- 哪类问题以前答错？
- 为什么答错？
- 做了什么修改？
- 修改后是否真的变好？
- 有没有把其他问题带坏？

## 二、整体阶段规划

### 第一阶段：建立可重复的评测基线

**目标：先知道系统现在有多好。**

新增一组固定评测问题，每条问题包含：

- 用户输入
- 期望遵守的策略
- 必须调用或禁止调用的工具
- 不允许出现的内容
- 可接受的回复特征

建议先准备 20～30 条，覆盖：

- 价格与优惠
- 能不能贴
- 效果能不能打包票
- 工期和施工方式
- 案例查询
- 资料缺失
- 工具报错
- 多轮上下文

每次修改策略后，自动跑一遍评测，记录：

- 策略命中率
- 规则遵守率
- 工具选择是否合理
- 转人工是否合理
- 回复是否出现新增问题

**阶段验收：** 能输出一份新旧版本对比结果，而不是只凭主观感受判断改好了没有。

### 第二阶段：策略版本、变更记录与回滚

**目标：让策略变化可追踪、可解释、可撤销。**

每次策略变化记录：

- 版本号
- 修改时间
- 修改来源
- 修改原因
- 修改前内容
- 修改后内容
- 影响的问题类型
- 评测结果

策略变更来源至少分三类：

1. 主动新增
2. 工单补充
3. 对话纠偏

**阶段验收：** 可以查看一次策略修改前后的差异；评测失败时可以回滚到上一版。

### 第三阶段：把运行轨迹变成真正的产品面板

**目标：让使用者一眼看懂智能体正在做什么。**

当前已有原始轨迹，下一步将它整理成状态面板：

- 当前问题
- 当前目标
- 已知事实
- 已命中的策略
- 已调用的工具
- 工具返回结果
- 是否发生重试
- 当前未解决的问题
- 最终结束原因
- 本轮是否产生新策略

建议把技术事件翻译成业务能看懂的文字：

```text
正在读取相关策略
正在核对汽车项目
项目信息未找到，准备转人工
本轮没有写入长期策略
```

**阶段验收：** 不看代码，只看页面，也能解释一轮咨询为什么这样回答。

### 第四阶段：结构化上下文与长会话压缩

**目标：避免把全部聊天历史直接塞给模型。**

新增一份结构化会话状态：

```json
{
  "用户背景": "2018 款 SUV，漆面有补漆",
  "当前目标": "全车改色，想要哑光",
  "所在城市": "北京",
  "已确认事实": ["全车改色一般留车 3 到 5 天"],
  "未解决问题": ["预算", "想要亮光还是哑光"],
  "当前策略": "先确认车型，不直接报价"
}
```

状态只保存对后续决策有用的信息，并保留来源消息，避免摘要失真后无法追溯。

**阶段验收：** 长对话经过压缩后，智能体仍能记住关键事实，并且能够指出这些事实来自哪一轮对话。

### 第五阶段：高风险动作闸门

**目标：不要把关键安全约束只交给提示词。**

以下动作增加确定性校验：

- 输出具体价格
- 做不起泡、不褪色这类结果承诺
- 对外发送消息
- 修改长期业务规则
- 删除策略或批量覆盖策略

模型可以提出动作，但系统先校验；高风险动作需要人工确认或满足明确条件后才能执行。

**阶段验收：** 即使模型判断错误，系统也能阻止高风险结果直接发出。

### 第六阶段：真实业务数据接入

**目标：把本地样例替换成可配置的数据源。**

接入顺序建议是：

1. 可配置的咨询场景资料
2. 汽车项目或产品信息接口
3. 案例和历史对话数据
4. 工单系统
5. CRM 或线索系统

这一步必须同时补充：

- 权限控制
- 数据脱敏
- 操作审计
- 租户隔离
- 数据版本
- 失败回退

在评测和策略版本没有稳定前，不建议直接接入真实客户消息。

## 三、每天更新的固定节奏

每天只做一个可以验证的小问题，建议控制在 1～3 小时内完成。

### 每日工作模板

```markdown
# 知返研发记录｜YYYY-MM-DD

## 今天要验证的问题

例如：策略样本增加后，价格问题是否仍然能召回正确策略？

## 当前现象

记录输入、实际回复、工具轨迹和不符合预期的地方。

## 我的判断

说明问题来自哪里：召回、提示词、上下文、工具、数据，还是页面表达。

## 今天做的最小修改

只记录真正改变行为的代码或数据修改。

## 修改前后对比

| 问题 | 修改前 | 修改后 | 是否达到预期 |
| --- | --- | --- | --- |
| 价格咨询 |  |  |  |

## 评测结果

- 通过：
- 失败：
- 新增问题：

## 今天的取舍

写清楚为什么暂时不做某个方向。

## 明天只验证一件事


```

### 每日更新不应该写什么

- 只写“优化了体验”
- 只写“增加了一个功能”
- 只贴代码截图，不说明行为变化
- 没有验证就说“智能体变聪明了”
- 把计划中的能力写成已经完成

## 四、建议的每周节奏

### 周一：提出假设

明确本周只验证一个工程问题，例如：

> 策略总纲变长后，是否会让模型更容易忽略硬规则？

### 周二至周三：实现最小改动

只修改解决假设所需的最小范围，避免同时改页面、提示词、数据库和模型适配层，导致无法判断结果来源。

### 周四：跑评测和失败案例

除了看通过率，也要专门看新增失败：一个问题变好后，是否让另一个问题变差。

### 周五：整理结论

写下：

- 假设是否成立
- 哪个方案被保留
- 哪个方案被推翻
- 当前还缺什么证据
- 下周验证什么

## 五、优先级排序

### 现在就做

1. 固定评测集
2. 评测结果记录
3. 策略版本和变更记录
4. 运行轨迹的产品化展示
5. 失败案例归档

### 评测稳定后再做

1. 结构化上下文状态
2. 长会话摘要
3. 高风险动作闸门
4. 策略冲突检测
5. 策略回滚

### 暂时不要做

- 多智能体协作
- 自动修改代码
- 复杂知识图谱
- 模型微调
- 花哨首页动画
- 没有评测依据的自动策略变异

这些方向不是永远不做，而是当前会分散注意力。知返首先要证明单一智能体闭环是可靠的。

## 六、最终希望达到的状态

当别人打开知返时，应该能看到一条完整证据链：

```text
一个问题以前答错
  ↓
运行轨迹显示错在哪里
  ↓
人工提出纠偏意见
  ↓
新策略生成并经过评测
  ↓
新版本通过更多测试
  ↓
页面展示策略确实发生了变化
```

这时知返才真正从“一个有想法的演示项目”，走向“一个有工程证据的自进化智能体原型”。
